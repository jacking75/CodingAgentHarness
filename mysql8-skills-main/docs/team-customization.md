# 팀별 설정을 공통 스킬과 분리하기

공통 스킬의 MySQL 검토 절차를 유지하고 프로젝트의 규칙만 별도 문서에 기록한다. 팀별 네이밍·FK 정책·ID 방식·격리 수준·시간대는 전사 사실로 가정하지 않는다.

## 반드시 먼저 정할 것

| 항목 | 이유 | 문서 |
|---|---|---|
| 대상 프로젝트·서비스와 정확한 DB 버전·배포판 | 잘못된 팀·버전의 기준 적용 방지 | team-profile.md |
| 스키마·쿼리·서버 코드·테스트 위치 | 실제 검토 근거 탐색 | team-profile.md |
| 팀 규칙과 예외의 담당자·유효 범위 | 권고를 강제 규칙으로 오해하지 않기 | team-rules.md |
| 실행 환경·허용 작업·승인 절차 | 파일 검토와 DB 실행 구분 | operations.md |

성능·확장 설계에서는 workload.md의 수치와 측정 시점을 추가로 채운다. 신규 팀에 모든 문서를 완벽히 작성하도록 요구하지 않는다. 모르는 항목은 `미정`으로 남기며 관련 판단만 제한한다.

## 설치 후 편집할 파일

- [부하 템플릿](../templates/workload.md): 수치·분포·불변식·접근 패턴.

## 경로 규약

사용자가 이번 작업에 지정한 프로필을 먼저 사용한다. 없으면 적용되는 AGENTS.md의 `DB_TEAM_PROFILE` 선언을 읽고, 그것도 없으면 프로젝트 루트 `docs/db/team-profile.md`를 찾는다. 이 문자열은 스킬이 읽는 텍스트 규약이며 환경변수나 Codex 설정 키가 아니다.

모노레포에서는 서비스마다 프로필을 두고 대상 서비스의 AGENTS.md 또는 호출문에서 정확한 프로필을 지정한다. 여러 후보를 발견했다고 첫 파일을 임의로 선택하지 않는다. 프로필에서 참조하는 상대 경로는 프로필 파일이 있는 디렉터리가 기준이다.

## 규칙의 성격과 충돌

규칙은 `필수 / 권고 / 예외`로 구분한다. DB의 실제 동작 사실은 팀 취향으로 덮어쓸 수 없다. 사용자 요청과 기존 승인은 존중하며, 팀 규칙과 충돌하면 해당 사실과 영향을 명시하고 적용 범위를 좁힌다. 보안 정책·실행 권한은 문서로 새로 부여되지 않는다.

예를 들어 FK 미사용을 팀 표준으로 정할 수는 있지만 참조 정합성 책임이 사라지는 것은 아니다. 스킬은 FK 추가를 무조건 요구하는 대신 애플리케이션·대사·삭제 절차의 보완을 검토해야 한다.

## 유지보수 책임

DA는 공통 규칙·예외 판단과 회귀 평가를 맡는다. 개발팀은 프로필·코드 경로·부하 변화의 최신성을 맡는다. 운영 담당은 실제 권한·복구 절차를 확인한다. 스킬 패키지 버전과 팀 프로필 버전은 따로 기록한다. 비밀이나 실사용자 데이터는 어떤 프로필에도 넣지 않는다.
