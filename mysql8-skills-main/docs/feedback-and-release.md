# 파일럿·피드백·배포 개선

## 첫 파일럿

개발팀 한 곳에서 schema-review, query-tuning, transaction-review부터 시작한다. 최초에는 결과를 참고 의견으로 사용하며 배포 차단이나 자동 운영 실행에 연결하지 않는다. 다른 스킬은 해당 업무가 있을 때 도입한다.

1. DA가 과거 사례를 비식별화하고 실제 문제와 허용 가능한 대안을 재검토한다.
2. 개발자는 실제 요청문·입력 버전·프로필·모델·시간을 기록한다.
3. DA는 유효한 지적과 누락, 잘못된 근거를 판정한다.
4. 공통 지침 문제인지 팀 정보 누락인지 구분해 수정한다.
5. 기존 사례와 별도 보관한 평가 사례를 재실행하고 배포 후보를 결정한다.

## 측정

- 중요 문제 탐지율 = 찾아낸 중요 문제 수 / 평가자가 확정한 중요 문제 수.
- 지적 정확도 = 유효 지적 수 / 판정한 전체 지적 수. 지적 0건이면 N/A다.
- 정보 부족을 적절히 표시한 비율과 허위 실행 주장 건수를 별도로 센다.
- 준비·응답 대기·사람 리뷰·수정까지 포함한 총시간을 비교한다. 코드 생성량은 목표가 아니다.
- 사례 수와 개별 실패를 함께 공개한다. 적은 사례의 백분율을 회사 전체 정확도로 표현하지 않는다.

## 변경 원칙

잘못된 행동을 최소 입력으로 재현하고 좁은 규칙을 고친다. 한 팀의 예외를 공통 강제 규칙으로 옮기지 않는다. 반복되는 중요한 실패가 있으면 해당 스킬의 적용 범위를 줄이고 미확인 결과로 처리한다.

## 배포 관문

프런트매터·링크·설치 구조 확인, 사례별 행동 평가, 승인되지 않은 DB 실행이나 허위 검증이 없는지를 확인한다. 허용할 탐지율·오탐·시간 기준은 파일럿 전 DA와 팀이 정한다. 정적 검사 통과만으로 실무 품질을 인증하지 않는다.

버전별 변경 파일·이유·평가 사례·잔여 한계를 CHANGELOG에 적는다. 0.x는 파일럿이며 프로젝트별 채택 버전을 고정한다. 팀 프로필은 별도 버전으로 관리한다. 이 문서가 정식 배포 승인서가 되는 것은 아니다.
